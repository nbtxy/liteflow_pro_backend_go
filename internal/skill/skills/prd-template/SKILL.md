# PRD 写作模板

一份 PRD（Product Requirements Document）的核心价值是让产品、技术、设计团队对"要做什么、为什么做、怎么衡量成败"达成共识。不是文档越厚越好，而是读完能让人动起来。

## 什么时候使用这个模板

适用的场景：
- 提出一个新产品或新功能
- 重构或迭代已有功能
- 给需求评审会准备材料

不适用的场景（不要套这个模板）：
- 一句话就能说清的小修小补（直接提 issue 就行）
- 纯技术改造（用技术方案模板而非 PRD）
- 探索性的点子（先写 one-pager，不要急着写 PRD）

## PRD 结构

按以下顺序组织，**前三节是核心**，其他按需补充。写完后回看，如果某节没有实质内容，就删掉——不要为了凑格式留空。

### 1. 背景与问题（Why）

回答"为什么要做这个"，必须讲清楚：
- 当前的用户/业务痛点是什么，有多严重（用数据说话）
- 如果不做会怎样
- 为什么现在做（时机）

**反面例子**："用户希望有更好的体验"——这是废话。

**正面例子**："目前用户创建新项目平均需要 7 步、2.3 分钟，数据显示 35% 的新用户在这个流程中流失。竞品 X 已经做到 3 步 30 秒。"

### 2. 目标用户与场景（Who & When）

- 主要目标用户是谁（角色、规模、特征）
- 典型使用场景（时间、地点、上下文、触发动机）
- **反例场景**：明确哪些用户或场景**不**是目标——这比列目标用户更能聚焦

### 3. 核心需求（What）

这是 PRD 的心脏。每条需求用用户故事或 Job-to-be-Done 格式：

```
作为 [用户角色]
我想要 [做什么]
以便 [达到什么目的]

验收标准：
- [ ] 具体的、可验证的条件 1
- [ ] 具体的、可验证的条件 2
```

**需求分级**：
- **P0（必须有）**：砍掉这个功能就不能上线
- **P1（应该有）**：上线后短期内补齐
- **P2（可以有）**：锦上添花，资源够就做

PRD 里的功能清单不要超过 10 条；如果超过，说明这不是一个功能而是一个项目，拆成多个 PRD。

### 4. 非目标（Non-Goals）

明确这次**不**做什么，避免范围蔓延。例如："本期不支持团队协作"、"不考虑移动端"。

没有"非目标"的 PRD 容易在执行过程中被塞进各种附加需求。

### 5. 成功指标（Metrics）

怎么判断上线后是成功还是失败：
- **北极星指标**：1 个，直接反映核心价值
- **辅助指标**：2-3 个，反映关键链路健康度
- **护栏指标**：1-2 个，防止优化一个指标牺牲了另一个（如提升注册转化但不能增加退订）

每个指标给出：当前值、目标值、目标时间。

### 6. 设计与交互（可选，如有设计稿附上）

关键交互流程、状态图、或设计稿链接。不要把每个页面都贴进 PRD——只放关键决策点。

### 7. 技术依赖与风险（可选）

- 依赖哪些上游系统或第三方服务
- 已知的技术限制
- 可预见的风险和缓解措施

### 8. 时间计划（可选）

关键里程碑，不要精确到天，用周或月。MVP 上线、灰度、全量的大致节点。

## 写作原则

**先写结论，再写论证**。每一节开头用 1-2 句话说清楚本节的核心结论，细节放后面。读者要能只读第一段就抓到要点。

**用数据不用形容词**。"体验差"换成具体的指标；"用户很需要"换成访谈数量或调研数据。

**能画图就不要纯文字**。流程用流程图，状态用状态图，数据用表格。

**主动质疑自己**。每写完一节反问：
- 如果用户只读这一节，ta 会不会误解我的意图？
- 有没有用默认大家都懂的黑话？
- 有没有把"怎么做"和"做什么"混在一起？（怎么做是技术方案，不是 PRD）

## 常见陷阱

| 陷阱 | 识别方式 | 修正方向 |
|---|---|---|
| 堆砌需求 | 列了 20 条功能 | 砍到 Top 5，其余降级到 P2 或拆分 |
| 混入技术方案 | 出现"用 Redis 缓存"、"调用 XX API" | 移到技术方案文档，PRD 只描述行为 |
| 目标太宏大 | "提升用户体验"、"打造最好的产品" | 换成可验证的指标 |
| 没有非目标 | 只有"要做什么"，没有"不做什么" | 补充 Non-Goals 章节 |
| 成功指标模糊 | "用户满意度提升" | 改为具体数值：NPS 从 32 提升到 45 |

## 快速起草清单

从零开始写 PRD 时，先花 10 分钟回答这 8 个问题，再开始填充模板：

1. 这个需求来自哪里？（用户反馈 / 数据观察 / 业务战略 / 技术限制）
2. 如果只能用一句话说清楚这个功能，是什么？
3. 谁是最主要的用户？他们现在怎么解决这个问题？
4. 上线后用什么指标判断成功？
5. 明确**不**做什么？
6. 预计需要多少人、多长时间？
7. 最大的风险是什么？
8. 如果老板说"只给你一周时间，交付最小的版本"，你会砍掉哪些需求？

回答完这 8 个问题，PRD 的骨架就有了。
