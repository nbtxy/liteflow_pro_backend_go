# 用户故事写作模板

用户故事不是需求的"缩写"，而是一种对话的起点。它刻意写得不完整，逼着产品、技术、设计在实现前把细节聊清楚。

## 什么时候用用户故事

适用场景：
- 把 PRD 中的功能拆成可执行的开发单元
- 构建产品 backlog，供 sprint 规划使用
- 跨职能团队对"具体要做什么"对齐

不适用场景：
- 技术债、重构、基础设施改造（用技术任务描述）
- Bug 修复（用 bug 报告模板）
- 探索性需求还没想清楚（先写 PRD 或 one-pager）

## 标准格式

每个用户故事包含三部分：**描述** + **验收标准** + **元信息**。

### 描述（Story Statement）

```
作为 [谁]
我想要 [做什么]
以便 [达到什么价值]
```

三要素缺一不可：
- **谁**：具体角色，不要写"用户"这种泛称。如"首次注册的独立开发者"比"用户"更有用
- **做什么**：用户视角的行为，不写技术实现。"通过邮箱登录"而不是"调用 OAuth 接口"
- **以便**：这个故事的价值。如果填不出来，说明这个故事可能不该做

### 验收标准（Acceptance Criteria）

推荐 Given-When-Then 格式：

```
场景 1：成功路径
  Given 用户已注册且未登录
  When  用户输入正确的邮箱和密码
  Then  系统跳转到主页并显示用户名

场景 2：密码错误
  Given 用户已注册且未登录
  When  用户输入错误的密码连续 5 次
  Then  系统锁定账户 15 分钟并发送警告邮件
```

**验收标准的数量**：3-7 条最合适。少于 3 条说明故事太粗，需要细化；多于 7 条说明故事太大，需要拆分。

### 元信息

- **Story ID**：便于追溯
- **优先级**：P0 / P1 / P2
- **估算**：Story Points（1, 2, 3, 5, 8, 13）或人天
- **依赖**：依赖哪些其他故事
- **关联需求**：所属 PRD 或 Epic

## INVEST 原则（好故事的六个特征）

每写完一个故事，用这六个字母自检：

| 字母 | 含义 | 检查问题 |
|---|---|---|
| **I**ndependent | 独立 | 能和其他故事分开开发吗？ |
| **N**egotiable | 可协商 | 细节能在实现前和团队讨论吗？ |
| **V**aluable | 有价值 | 完成后用户或业务得到什么？ |
| **E**stimable | 可估算 | 团队能估出工作量吗？ |
| **S**mall | 小 | 能在一个 sprint 内完成吗？ |
| **T**estable | 可测试 | 验收标准足够具体吗？ |

任何一条不满足，都是拆分或修改的信号。

## 故事拆分技巧（故事太大时怎么办）

当一个故事估算超过 13 个 story points 或 5 人天，就需要拆。七种常见拆分方式：

1. **按工作流步骤**：注册流程拆成"填邮箱 → 验证邮箱 → 填用户名 → 完成注册"四个故事
2. **按业务规则**：基础权限校验先做，高级权限规则后做
3. **按数据变体**：先支持导入 CSV，再支持 Excel，再支持 JSON
4. **按接口**：先做 API，再做网页端，再做移动端
5. **按性能要求**：先做能跑通，再优化到 200ms 以内
6. **按用户类型**：先支持普通用户，再支持管理员
7. **Happy Path 先行**：先只处理正常流程，异常处理另起故事

## 常见陷阱

| 陷阱 | 识别方式 | 修正方向 |
|---|---|---|
| 技术故事伪装成用户故事 | "作为开发者，我想要重构登录模块" | 转为技术任务，不套用户故事格式 |
| 价值缺失 | "以便" 部分写"提升体验" | 改为可感知的具体价值 |
| 角色过于抽象 | "作为用户..." | 细化到具体用户细分 |
| 混入实现细节 | 描述里有"数据库"、"API"、"缓存" | 挪到技术方案，故事只描述行为 |
| 验收标准太少 | 只有 1-2 条 | 补充异常场景和边界条件 |
| 故事太大 | 估算超过 13 points | 用拆分技巧拆成多个 |
| 和产品脱节 | 没有关联到 PRD 或 Epic | 补充元信息中的关联字段 |

## 快速示例

```
Story ID: LF-001
优先级: P0
估算: 3 points
关联需求: LiteFlow v1.0 - 用户认证

描述:
作为首次访问 LiteFlow 的独立开发者
我想要用邮箱快速注册账号
以便立刻开始使用产品，不被冗长的表单劝退

验收标准:
场景 1：正常注册
  Given 用户访问注册页面
  When  用户输入有效邮箱和密码（至少 8 位，含字母和数字）
  Then  系统发送验证邮件，并跳转到"请查收邮件"页面

场景 2：邮箱已注册
  Given 用户输入的邮箱已被注册
  When  用户点击注册按钮
  Then  系统提示"邮箱已注册，请直接登录"并提供登录入口

场景 3：密码强度不足
  Given 用户输入的密码少于 8 位或不含数字
  When  用户尝试提交
  Then  系统实时显示密码强度提示，提交按钮保持禁用

场景 4：邮箱格式错误
  Given 用户输入的邮箱格式不合法
  When  用户离开邮箱输入框
  Then  输入框下方显示"请输入有效的邮箱地址"

依赖: 无
```

## 起草清单

写一批用户故事前，先回答：

1. 这批故事对应哪个 PRD 或 Epic？
2. 主要目标用户是谁？（越具体越好）
3. 用户的核心工作流是什么？列出关键步骤
4. 每个步骤对应一个故事吗？还是需要进一步拆分？
5. 哪些故事是 P0（MVP 必须）？哪些可以延后？
6. 是否有故事之间的依赖？（画依赖图避免循环依赖）

回答完这 6 个问题再开始写，避免写到一半发现故事之间结构混乱。
