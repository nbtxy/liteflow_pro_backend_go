# 架构设计模板

架构设计的本质是**在约束下做权衡**——没有"最好的架构"，只有"适合当下的架构"。好的架构文档不是展示你有多懂技术，而是让读者理解**为什么是这样而不是那样**。

## 什么时候写架构文档

适用场景：
- 新系统从零开始设计
- 现有系统重大重构
- 跨团队协作，需要对齐接口和职责
- 复杂度高到一句话说不清

不适用场景：
- 单模块的内部实现（用技术方案文档）
- 小改动（直接写代码或 issue）

## 在开始画图之前

架构文档经常犯的错是**直接开画框图**。先花 30 分钟回答这些问题：

### 1. 需求是什么（不是技术需求，是业务需求）

- 这个系统要解决什么业务问题？
- 主要用户 / 使用方是谁？
- 规模预期：用户数、请求量、数据量、增长速度
- 上线时间约束

### 2. 关键质量属性（Non-Functional Requirements）

不要说"要高可用、高性能"。**量化**：

- **可用性**：99.9% 还是 99.99%？年度停机时长
- **延迟**：P50 / P95 / P99 分别要多少 ms？
- **吞吐**：QPS / TPS 峰值多少？
- **数据量**：总量、日增、单记录大小
- **一致性**：强一致 / 最终一致 / 可容忍 N 秒延迟？
- **安全**：数据敏感级别、合规要求
- **扩展性**：2 倍 / 10 倍 / 100 倍流量要怎么扩？

这些直接决定架构选型。"高可用" vs "99.95%" 差了一万倍成本。

### 3. 约束

- 预算（人、钱、机器）
- 团队技术栈（团队会 Go 还是 Java？）
- 时间（一周原型 vs 半年精品）
- 外部依赖（必须接入的系统）
- 合规 / 法律要求

## 架构文档结构

按以下顺序，前 5 节必写。

### 1. 背景与目标

一段话说清楚：
- 这个系统是什么、解决什么问题
- 和现有系统的关系
- 本文档的范围（包含什么、不包含什么）

### 2. 需求与约束

- **功能需求**：3-5 句话列出核心能力，不是罗列所有功能
- **非功能需求**：前面第 2 步的量化指标
- **约束**：预算、技术栈、时间等

### 3. 整体架构

**一张高层架构图 + 每个组件一段话说明**。

架构图要素：
- 组件（用框表示）
- 数据流（用箭头表示，标注方向和协议）
- 外部依赖（单独画区分）
- 清晰的边界（什么是系统内、什么是系统外）

一段说明包括：
- 组件的职责
- 核心技术选型
- 对其他组件的依赖

**避免的坑**：
- 不要画得像电路图——15 个组件在一张图上没人看得懂
- 如果组件多，分层画（高层总览 + 各层详图）
- 避免抽象的"Service"、"Manager"命名，用业务语言

### 4. 核心数据流

挑 2-4 个**最核心的场景**，用时序图或流程图画出端到端数据流。

每个流程说明：
- 触发条件
- 涉及哪些组件
- 关键数据结构
- 失败场景怎么处理

示例场景：
- "用户注册"
- "一次查询请求的完整链路"
- "一次支付的全流程（含失败回滚）"

### 5. 技术选型

**每个关键选型必须说明理由**，不能只列结果。模板：

```
## 存储选型

选择：PostgreSQL

对比选项：
- MySQL：团队不熟，JSON 支持弱
- MongoDB：不需要 schema 自由，事务支持是硬需求
- PostgreSQL：团队熟悉，JSON + 事务兼得

决策理由：
主要场景是结构化数据 + 少量 JSON 字段，需要事务。
团队有 PG 经验，避免引入新组件增加运维成本。

风险与缓解：
- 大表性能可能成为瓶颈 → 预留分库分表方案
- 单点故障 → 主从 + 每日备份
```

**常见选型决策点**：
- 数据库（关系 vs 文档 vs 时序 vs 搜索）
- 消息队列（Kafka vs RabbitMQ vs NATS vs 无）
- 缓存（Redis vs Memcached vs 本地缓存）
- 通信协议（HTTP vs gRPC vs WebSocket）
- 部署（单机 vs K8s vs Serverless）
- 编程语言 / 框架

### 6. 数据模型

关键表 / 集合的 schema，重点是：
- 核心实体和关系
- 索引策略
- 分区 / 分片策略（如果需要）
- 数据生命周期（归档、删除）

不要把每张表都写进来，挑 3-5 个最关键的。

### 7. 关键设计决策（Trade-offs）

单独一节记录重要的权衡。每条决策包括：
- **问题**：什么场景下的什么冲突
- **选项**：考虑过哪些方案
- **选择**：最终选了哪个
- **代价**：放弃了什么
- **复核条件**：什么情况下需要重新评估

这节是架构文档**最有价值**的部分。半年后有人质疑某个决策时，能直接看到当时的权衡上下文。

### 8. 部署架构

- 部署拓扑图
- 环境分层（dev / staging / prod）
- CI/CD 流程
- 机器配置估算
- 成本估算

### 9. 可观测性

- 日志：记录哪些、存哪里、保留多久
- 指标：业务指标、技术指标
- 追踪：分布式 tracing 策略
- 告警：哪些指标告警、通知谁

### 10. 风险与未解决问题

诚实列出：
- 已知风险及缓解措施
- 还没想清楚的问题
- 依赖外部团队 / 资源的部分

这节体现了设计者的成熟度。没有"完美的架构"，装作完美反而会让读者怀疑你的判断。

## 设计原则（判断是否合理的标准）

写完后用这些原则自检：

### 可以为之付出代价的

- **简单**：能用一个组件不要用两个。每多一个组件都增加运维成本
- **清晰边界**：每个组件职责单一，能单独部署、升级、替换
- **依赖方向**：高层依赖低层，不要反向；能单向就不要双向
- **数据所有权**：每份数据只有一个 source of truth
- **失败隔离**：一个组件挂了不影响其他，降级优雅

### 警惕的信号

- **过早分布式**：单机能搞定的强行微服务化
- **过早抽象**:为了可能的未来需求引入大量接口
- **技术驱动**:用了 Kafka 因为好玩不是因为需要异步
- **同步链太长**:A 同步调 B，B 同步调 C，C 同步调 D，任何一环挂全挂
- **没有退路**:选了一个技术后就没法换了
- **观测性是事后**:系统上线后再加日志和监控

## 常见陷阱

| 陷阱 | 症状 | 修正 |
|---|---|---|
| 先画图后想需求 | 精美的架构图解决错误的问题 | 先量化非功能需求 |
| 过度设计 | MVP 就上微服务、消息队列、多级缓存 | 按当前规模 10x 设计，不是 100x |
| 忽略运维 | 没考虑部署、监控、故障排查 | 每个组件问"挂了怎么办、怎么发现" |
| 选型没理由 | "用 XX 因为流行" | 对比至少 2 个选项，写权衡 |
| 忽略成本 | 方案很酷但月花十万 | 加上成本估算 |
| 没有非目标 | 试图一个系统解决所有问题 | 明确不做什么 |

## 快速起草清单

动手画图前先回答：

1. 这个系统要解决什么业务问题？（一句话）
2. 规模：QPS、数据量、用户数各是多少？（量化）
3. 最关键的 3 个非功能要求是什么？
4. 团队擅长什么技术栈？
5. 预算约束（人 / 时间 / 钱）是什么？
6. 有哪些外部依赖不能改？
7. 6 个月后最可能失败的是哪里？
8. 如果只能选一个最重要的设计决策，是什么？
