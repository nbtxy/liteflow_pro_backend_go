# 技术方案模板

技术方案（Tech Spec）和架构设计不是一回事。架构解决**系统级**问题（多个模块怎么协作），技术方案解决**模块级**问题（具体功能怎么实现）。本模板针对技术方案。

## 技术方案 vs 架构设计 vs PRD

| 文档 | 回答的问题 | 读者 | 粒度 |
|---|---|---|---|
| PRD | 做什么 / 为什么做 | 产品 + 技术 + 设计 | 功能 |
| 架构设计 | 系统整体怎么组织 | 技术团队 | 系统 |
| 技术方案 | 某个功能怎么实现 | 开发者 + Reviewer | 模块 |

如果你要写的是"XX 系统怎么搭"，用架构模板。如果是"XX 功能怎么做"，用这个。

## 什么时候写技术方案

适用场景：
- 实现一个有一定复杂度的功能（需要改多个文件 / 引入新依赖 / 改动数据模型）
- 改动可能影响其他模块
- 多人协作的功能
- 方案有多个选项需要讨论

不适用场景：
- 简单 bug 修复
- 单文件的小改动
- 纯重构（用重构提案）

## 技术方案结构

按顺序组织，**前 4 节是核心**。

### 1. 背景与目标

- **要解决的问题**：2-3 句话说清楚当前痛点
- **关联需求**：链接到 PRD 或 issue
- **成功标准**：实现完成后如何判断成功（可验证）
- **非目标**：这次**不**解决什么

### 2. 方案概述

一段话概括方案的核心思路。读者看完这段应该能复述方案的大致做法。

示例："通过在消息表新增 `agent_id` 字段记录每条消息的 Agent 归属，配合文件方式加载 Agent 配置，实现主 Agent 调度子 Agent 的多 Agent 架构。"

### 3. 方案对比（如果有多个方案）

如果方案是唯一的、没有其他选项，跳过这节。如果有多个选项，必须对比。

模板：

```
## 方案对比

### 方案 A：文件管理 Agent 配置
优点：
- 版本可控，适合 code review
- 改动不需要数据库迁移
缺点：
- 不支持运行时动态修改
- 每次改动需要重启服务

### 方案 B：数据库管理 Agent 配置
优点：
- 支持 admin UI 动态修改
- 多环境可独立配置
缺点：
- 改 prompt 需要写迁移
- 没法 code review
- 多环境配置漂移

### 选择：方案 A
理由：
- Agent 数量少（< 10）、变更频率低
- 改 system_prompt 影响所有用户，需要 code review
- MVP 阶段没有 admin UI 需求

放弃的代价：
- 非技术人员无法通过界面修改 Agent（可接受，当前团队都是开发者）
```

**关键**：写清楚"放弃的代价"。没有代价的选择都是可疑的。

### 4. 详细设计

这是方案的核心。根据功能特性，按需包含以下子节：

#### 4.1 数据模型变更

```sql
-- 明确的 DDL
ALTER TABLE messages ADD COLUMN agent_id VARCHAR(50);
CREATE INDEX idx_messages_agent ON messages(agent_id);
```

说明：
- 为什么这样设计（比如"为什么用 VARCHAR(50) 而不是 UUID"）
- 和现有数据的兼容性（已有数据怎么处理）
- 索引策略

#### 4.2 API 设计

每个新 API 或修改的 API：

```
POST /api/conversations/:id/messages
Request:
  {
    "content": string,     // 用户输入内容
    "attachments": []string // 附件 URL 列表，可选
  }
Response:
  {
    "id": string,
    "content": string,
    "agent_id": string,    // 新增字段
    "delegations": [...]   // 新增字段
  }
```

说明：
- 向后兼容性（新字段是否破坏老客户端）
- 错误码设计
- 鉴权要求

#### 4.3 核心逻辑 / 算法

关键代码的伪代码或结构图：

```go
func (s *Service) Resolve(ctx, agentID) (*AgentRuntime, error) {
    agent := registry.Get(agentID)
    rt := buildRuntime(agent)
    if agent.Type == "main" {
        // 注入所有子 Agent 作为 delegate tools
        for _, sub := range registry.Subs() {
            rt.Tools = append(rt.Tools, buildDelegateTool(sub))
        }
    }
    return rt, nil
}
```

不要贴完整代码。重点是说明**思路**，细节在 PR 里。

#### 4.4 状态 / 流程

如果涉及状态机或复杂流程，用图说明：

```
用户消息
   ↓
主 Agent Resolve
   ↓
Context 组装（含 delegate tools）
   ↓
LLM 调用 → [有 tool_call？]
           ├ 是 → 执行 tool → 流式推送 → 回到 LLM
           └ 否 → 返回结果
```

#### 4.5 关键技术点

每个有难度的点单独说明：

- 问题描述
- 解决思路
- 技术细节
- 边界情况处理

### 5. 影响面分析

- **直接影响**：改动涉及哪些模块 / 文件
- **间接影响**：上下游系统需要配合改动吗
- **用户影响**：对现有用户有什么感知变化
- **回滚影响**：如果出问题回滚会不会丢数据

### 6. 迁移与兼容性

如果涉及数据或 API 变更：

- 历史数据怎么处理（默认值 / 数据回填 / 保留原样）
- 灰度策略（按用户 / 按流量 / 按环境）
- 老客户端兼容性
- 回滚方案

### 7. 测试方案

- **单元测试**：哪些核心逻辑要测
- **集成测试**：哪些跨模块流程要测
- **手工测试 / 验收场景**：QA 或产品需要验证的关键场景
- **性能测试**：如果有性能要求，怎么验证

不必列出每个测试用例，列关键场景即可。

### 8. 监控与告警

上线后怎么知道方案跑得好不好：

- 业务指标（使用率、成功率）
- 技术指标（延迟、错误率、资源占用）
- 告警阈值和响应流程

### 9. 发布计划

- **开发工作量估算**：按模块拆分
- **依赖顺序**：哪些先做、哪些并行
- **发布步骤**：DB 迁移 → 服务发布 → 功能开关打开
- **灰度节奏**：1% → 10% → 50% → 100%

### 10. 风险与未解决问题

诚实列出：
- 可预见的风险及缓解
- 还在调研的技术点
- 依赖其他团队的部分

## 评审清单

写完技术方案自检：

**需求维度**
- [ ] 我真的理解要解决的问题吗？
- [ ] 成功标准是可验证的吗？
- [ ] 非目标明确了吗？

**方案维度**
- [ ] 有没有考虑过至少一个替代方案？
- [ ] 选择的理由是否经得起推敲？
- [ ] 放弃的代价我能接受吗？

**实现维度**
- [ ] 数据模型变更向后兼容吗？
- [ ] API 变更会不会破坏老客户端？
- [ ] 核心逻辑读者能理解吗？
- [ ] 边界情况（空、超时、失败）考虑了吗？

**运维维度**
- [ ] 上线后能观测到异常吗？
- [ ] 出问题能快速定位和回滚吗？
- [ ] 有没有性能或成本陷阱？

**协作维度**
- [ ] 影响的其他团队知道这个方案吗？
- [ ] 工作量估算合理吗？
- [ ] 风险列全了吗？

## 常见陷阱

| 陷阱 | 症状 | 修正 |
|---|---|---|
| 跳过问题定义 | 直接写实现细节 | 补充"为什么要做"和"成功标准" |
| 单一方案 | 只写选了什么，没比较 | 至少列一个对比方案和放弃理由 |
| 过度设计 | 为将来可能的需求做抽象 | 只设计当前确定的需求 |
| 忽略迁移 | 不说老数据怎么办 | 明确数据迁移和兼容方案 |
| 没有回滚方案 | 只考虑成功路径 | 每次变更都要有回滚路径 |
| 影响面不清 | 改了但别人不知道 | 主动通知上下游 |
| 无可验证标准 | 上线后不知道成没成功 | 定义可量化的指标 |

## 快速起草清单

动手前先回答：

1. 这个方案要解决什么问题？（一句话）
2. 对应的 PRD 或 issue 是什么？
3. 成功标准是什么？（可验证）
4. 有几种方案？为什么选这个？
5. 需要改数据模型吗？怎么兼容老数据？
6. 需要改 API 吗？老客户端影响？
7. 上线后怎么监控效果？
8. 最可能出问题的地方是哪里？回滚方案是什么？

回答完这 8 个问题，技术方案的骨架就有了。
