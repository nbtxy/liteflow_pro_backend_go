# 代码审查清单

好的 code review 不是"挑错"，而是**在缺陷变成事故之前拦截它，同时传递团队的工程品味**。坏的 review 只盯着空格和变量名。

## 审查优先级（从高到低）

Review 时间有限，按这个顺序看，**高优先级问题先解决**：

1. **正确性**：代码逻辑对不对，有没有 bug
2. **安全性**：有没有可被利用的漏洞
3. **数据安全**：会不会丢数据、脏数据、权限越界
4. **设计合理性**：架构、接口、抽象是否合理
5. **性能**：是否有明显性能问题
6. **可读性**：别人能不能看懂
7. **可测试性**：测试是否充分
8. **风格**：命名、格式、注释

前 4 项是**必改**的。后 4 项是**建议改**，不阻塞合入。

## 一、正确性

### 核心问题

- [ ] **逻辑是否正确**：对照需求，代码真的实现了需求吗？
- [ ] **边界条件**：空输入、null、空数组、超长字符串、极大极小数字、零值
- [ ] **错误处理**：错误是吞了、打日志了、还是抛了？抛给谁处理？
- [ ] **并发安全**：多个 goroutine / 线程同时调用会怎样？共享状态怎么保护？
- [ ] **事务性**：多步操作中间失败了，状态会不会半吊子？
- [ ] **幂等性**：重试同一个请求会不会产生重复副作用？
- [ ] **空指针 / nil 检查**：可能为 nil 的值在使用前检查了吗？
- [ ] **索引越界**：数组和切片访问前检查长度了吗？
- [ ] **类型转换**：强转可能失败吗？int/float 转换有精度丢失吗？

### 常见陷阱

- `if err != nil` 后忘记 return
- defer 在循环里累积资源
- map 并发读写
- 浮点数直接比较相等
- 时区问题（UTC vs 本地时间）
- 字符串拼接 SQL（SQL 注入）

## 二、安全性

### 输入验证

- [ ] 所有外部输入（HTTP 请求、文件、环境变量）都校验了吗？
- [ ] 长度、格式、范围都有限制吗？
- [ ] 特殊字符是否正确转义？

### 注入防护

- [ ] SQL：用参数化查询而非字符串拼接
- [ ] 命令执行：避免 `exec(userInput)`
- [ ] HTML：输出到页面时转义
- [ ] 日志：不要把用户输入直接写入日志（日志注入）

### 认证与授权

- [ ] 每个需要权限的操作都做了鉴权吗？
- [ ] 鉴权逻辑在服务端而非客户端吗？
- [ ] 横向越权：用户 A 能否操作用户 B 的数据？
- [ ] 纵向越权：普通用户能否调用管理员接口？

### 敏感信息

- [ ] 密码是否哈希存储（bcrypt/argon2，不是 MD5/SHA1）？
- [ ] API key、token 是否写进了代码或日志？
- [ ] 错误消息是否泄露内部实现（堆栈、SQL、文件路径）？
- [ ] 返回给前端的数据是否包含不该暴露的字段（password_hash、internal_id）？

## 三、数据安全

- [ ] **删除操作**：有没有二次确认 / 软删除 / 恢复机制？
- [ ] **批量操作**：有没有上限保护，防止误删全表？
- [ ] **迁移**：DB 迁移有回滚方案吗？破坏性变更有审批吗？
- [ ] **事务**：跨资源操作有没有补偿机制？
- [ ] **外部 API**：依赖的外部服务挂了，我们的数据会不会损坏？
- [ ] **时序**：先写 DB 还是先发消息？失败了怎么办？

## 四、设计合理性

### 接口设计

- [ ] 函数名、参数名是否清晰表达意图？
- [ ] 参数是否过多（超过 4 个就考虑拆分或用 option 结构）？
- [ ] 返回值是否清晰（多返回值 vs 错误 vs 结构体）？
- [ ] 是否有副作用（函数名没提到但改了全局状态）？

### 抽象层次

- [ ] 是否混了业务逻辑和底层实现（HTTP handler 里直接写 SQL）？
- [ ] 重复代码是否应该提取？但也要警惕过早抽象
- [ ] 对外接口是否稳定（public API 的兼容性）？

### 依赖

- [ ] 依赖方向是否合理（高层 → 低层，不要反向）？
- [ ] 是否引入了不必要的重依赖？
- [ ] 依赖注入是否到位（便于测试）？

## 五、性能

关注**明显问题**即可，不要过早优化：

- [ ] **循环内的 DB 查询（N+1）**：能不能改成批量查询？
- [ ] **没有分页**：返回列表接口有 limit 吗？
- [ ] **索引缺失**：新加的 WHERE 条件有索引吗？
- [ ] **大对象在内存中**：能不能流式处理？
- [ ] **不必要的重复计算**：循环内能提取的常量
- [ ] **阻塞调用**：在热路径上有同步 HTTP/IO 吗？
- [ ] **资源释放**：文件、连接、锁都在 defer / finally 里释放了吗？

## 六、可读性

- [ ] **命名**：变量和函数名能自解释吗？`x`、`data`、`obj` 都是红旗
- [ ] **函数长度**：超过 50 行通常要拆分
- [ ] **嵌套深度**：超过 3 层需要提前 return 或抽函数
- [ ] **注释**：解释"为什么"而不是"是什么"。代码本身应该说明"是什么"
- [ ] **魔法数字**：`if count > 7`，7 是什么？提取成命名常量
- [ ] **死代码**：注释掉的代码、不再调用的函数都应该删除

## 七、可测试性

- [ ] **有测试吗**：新增逻辑有对应的测试吗？
- [ ] **测试覆盖关键路径**：核心逻辑、边界条件、错误路径都测了吗？
- [ ] **测试可读**：测试名能说明测的是什么吗？
- [ ] **mock 合理**：mock 的是依赖边界还是内部实现？
- [ ] **flaky 测试**：有没有依赖时间、网络、并发顺序导致不稳定？

## 八、语言特定陷阱

### Go
- [ ] goroutine 泄漏：启动了没有退出机制的 goroutine
- [ ] channel 死锁：单向阻塞、无关闭
- [ ] defer 在循环里
- [ ] range 循环变量在 goroutine 里（Go 1.22 前）
- [ ] 错误包装：用 `fmt.Errorf("...: %w", err)` 保留错误链
- [ ] 接口 nil：`var err error = (*MyErr)(nil); err != nil` 是 true

### Java / Spring
- [ ] `@Transactional` 自调用失效
- [ ] 异常被 `catch (Exception e)` 吞掉
- [ ] Stream 未 close
- [ ] equals/hashCode 成对实现
- [ ] Optional 滥用（字段、参数不要用 Optional）

### Python
- [ ] mutable default argument（`def f(x=[])`）
- [ ] 异常只 `except:` 不写类型
- [ ] 字符串拼接大循环（用 `"".join`）
- [ ] 忘记 `close()` 或 `with` 语句

### JavaScript / TypeScript
- [ ] `==` vs `===`
- [ ] async 函数忘记 await
- [ ] 未处理的 Promise rejection
- [ ] `any` 类型泛滥
- [ ] null / undefined 没区分

## Review 的沟通原则

Review 是协作不是评判：

- **具体而非泛泛**：说"第 42 行 N+1 查询"而不是"性能有问题"
- **解释理由**：说"用 X 更好，因为 Y"而不是"改成 X"
- **区分必改和建议**：标注 `[blocker]` / `[nit]` 让作者知道优先级
- **夸好代码**：看到巧妙的设计要明说，不要只挑错
- **问问题而非命令**：`有没有考虑过 X 的情况？` 比 `你应该用 X` 更开放
- **承认不确定**：`我不太确定，但这里是不是可能有 race condition？` 比硬下结论好

## 快速 Review 清单（适合小 PR）

时间紧的时候，按这五个问题扫一遍：

1. **这段代码实现的需求和 PR 描述一致吗？**
2. **有没有明显的 bug 或边界条件没处理？**
3. **有没有安全问题（注入、越权、敏感信息泄露）？**
4. **有没有测试？测试覆盖到关键路径了吗？**
5. **我自己 debug 这段代码会有多困难？**

这五个问题过完，80% 的问题能抓住。
